# 壹.2.2 作用域、执行上下文、作用域链

作用域决定变量在哪里可见，执行上下文解释代码运行时的环境，作用域链决定找不到变量时去哪儿找。概念不难，但混在一起就容易把代码执行结果猜错。

## 壹.2.2.1 作用域（Scope）

**作用域就是变量和函数能被访问的范围。**

### 函数作用域

函数内部有自己的作用域，外部代码通常不能直接读取函数内部声明的局部变量。

```javascript
var a = "coffe";//在全局作用域
function func(){
    var b="coffe";//在函数作用域内
    console.log(a);
}

console.log(a); // coffe
func();         // coffe
try {
    console.log(b);
} catch (error) {
    console.log(error.name); // ReferenceError
}
```

`a` 在外层，`func` 可以读取；`b` 只在函数内部，外部访问会抛 `ReferenceError`。示例用 `try...catch` 避免错误中断后续代码。

```javascript
//全局作用域

function func(){//作用域A
    var a = "coffe";

    function func1(){//作用域B。定义一个函数，把不想公开的内容隐藏起来
        var a = "1891";//这里的 a 遮蔽了外层同名变量，并没有修改外层 a
        var b = "b";

        //这里可以放有很多其他要对外隐藏的内容：变量或者函数
        //……
        //…

        console.log(a);
    }

    console.log(a); // coffe
    func1();       // 1891
    try {
        console.log(b);
    } catch (error) {
        console.log(error.name); // ReferenceError：b 在内层函数里
    }
}
func(); // 依次输出 coffe、1891、ReferenceError
```

外层 `a` 是 `"coffe"`，`func1` 内部的同名变量是 `"1891"`。**内层变量遮蔽外层变量，并没有改写它。**

旧式脚本还常用立即执行函数（IIFE）隔离变量：

```javascript
//全局作用域

function func(){//作用域A
    var a = "coffe";

    (function(){//作用域B。一个IIFE形式的函数，把不想公开的内容隐藏起来
        var a = "1891";
        var b = "b";

        //这里可以放有很多其他要对外隐藏的内容：变量或者函数
        //……
        //…

        console.log(a);
    })();//>> 1891

    console.log(a); // coffe
    try {
        console.log(b);
    } catch (error) {
        console.log(error.name); // ReferenceError
    }
}
func(); // 依次输出 1891、coffe、ReferenceError
```

现代 ES Module 自带模块作用域，不必每段代码都套 IIFE。

### ES6 带来了块级作用域，顺便留下一个容易踩的坑

以前写 `var`，变量的作用范围主要是函数或者全局。到了 ES2015，`let` 和 `const` 允许你把变量的作用范围限定在 `{ }` 里面。

```javascript
{
  const scopeSecret = 'coffe';
  let count = 1;
  count++;
  console.log(scopeSecret, count); // coffe 2
}
// console.log(scopeSecret); // ReferenceError：块外访问不到这个变量
```

块内函数声明在非严格脚本中存在历史兼容行为；**严格模式和 ES Module 按块级作用域处理**。不能拿普通脚本的特殊结果推断所有环境：

```javascript
'use strict';
{
  function onlyInside() { return 1; }
  console.log(onlyInside()); // 1
}
try {
  console.log(onlyInside());
} catch (error) {
  console.log(error.name); // ReferenceError
}
```

块内声明优先使用 `const`、`let`；排查旧代码时先确认是否处于严格模式。

参考：[MDN：function 声明与块级作用域](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/function)。

### 为什么要引进块级作用域？

`let`、`const` 能限制变量范围，还能避免一部分 `var` 带来的意外访问。看一个变量提升的例子：

```javascript
(function() {
  console.log(a); //>> undefined
  try {
    console.log(b);
  } catch (error) {
    console.log(error.name); // ReferenceError（暂时性死区）
  }
  var a = "coffe"; //声明提前
  let b = "1891"; // 此前读取 b 会触发暂时性死区（TDZ）的 ReferenceError
})();
```

上面这段代码里，`var a` 的绑定会在进入函数时建立，赋值仍发生在原本那行，所以提前读取会得到 `undefined`。而 `let b` 的绑定同样与作用域有关，**只是从块开始到初始化之前处于暂时性死区（TDZ）**，提前读取会直接抛 `ReferenceError`。严格来说，不能简单地教成“var 会提升，let 完全不提升”。这也是为什么建议在声明之后再使用变量。

另一个区别是循环变量的作用域：

```javascript
(function() {
  for (var i = 0; i < 100; i++) {
    //……很多行代码
  }
  function func() {
    //……很多行代码
  }
  //……很多行代码
  console.log(i); //>> 100
})();
```

`var i` 在循环结束后仍属于所在函数的作用域，后面的代码还能访问它，这才是这里真正的“污染”。**不要据此推断 `let` 一定比 `var` 回收得更快。** 变量实际能否被垃圾回收，要看它是否仍然可达，而不是只看用哪个关键字声明。

```javascript
(function() {
  for (let i = 0; i < 100; i++) {
    //……很多行代码
  }
  function func() {
    //……很多行代码
  }
  //……很多行代码
  console.log(i); //>> ReferenceError
})();
```

综上，现代代码里**默认用 `const`，确实需要重新赋值再用 `let`，尽量避免 `var`**。想定义跨模块共享的状态，也不应该靠随手污染全局变量来解决。

## 壹.2.2.2 执行上下文（Execution Context）

### 定义

执行上下文描述 JavaScript 代码执行时的环境，涉及变量绑定、词法环境和 `this` 等信息。它是规范层面的抽象，不必把它理解成某个浏览器里固定的对象结构。

![](../.gitbook/assets/image%20%2816%29.png)

### 类型

执行上下文总共有三种类型：

* **全局执行上下文**：用于执行顶层代码，但不能简单把所有环境的顶层 `this` 都说成 `window`。例如，浏览器普通脚本与 ES Module 的顶层 `this` 行为不同；在 ES Module 顶层它是 `undefined`。
* **函数执行上下文**：每次调用函数时，都会为该函数创建一个新的执行上下文。每个函数都拥有自己的执行上下文，但是只有在函数被调用的时候才会被创建。一个程序中可以存在任意数量的函数执行上下文。每当一个新的执行上下文被创建，它都会按照特定的顺序执行一系列步骤，具体过程将在本文后面讨论。
* eval执行上下文：运行在 eval 函数中的代码也获得了自己的执行上下文，ES6 之后不再推荐使用 eval 函数，所以本书出于面试实用考虑，不会深入讨论eval。

### 执行上下文的生命周期

执行上下文的生命周期包括三个阶段：创建阶段 → 执行阶段 → 回收阶段，本文重点介绍创建阶段。

#### a. 创建阶段

当函数被调用，但未执行任何其内部代码之前，会做以下三件事：

* 创建变量对象：首先初始化函数的参数 arguments，提升函数声明和变量声明（变量的**声明提前**有赖于`var`关键字）。
* 创建作用域链：在执行期上下文的创建阶段，作用域链是在变量对象之后创建的。作用域链本身包含变量对象。作用域链用于解析变量。当被要求解析变量时，JavaScript 始终从代码嵌套的最内层开始，如果最内层没有找到变量，就会跳转到上一层父作用域中查找，直到找到该变量。
* 确定 this 指向。

#### b. 执行阶段

创建完成之后，就会开始执行代码，在这个阶段，会完成变量赋值、函数引用、以及执行其他代码。

#### c. 回收阶段

函数返回后，其执行上下文通常出栈；**被闭包引用的数据仍可能保留**，不能简单说函数返回就销毁所有相关数据。

![](../.gitbook/assets/image%20%2838%29.png)

### 执行上下文栈

```javascript
var a = "coffe"; //1.进入全局执行上下文
function out() {
    var b = "18";
    function inner() {
        var c = "91";
        console.log(a+b+c);
    }
    inner(); //3.进入inner函数的执行上下文
}
out(); //2.进入out函数的执行上下文
```

代码执行时先进入全局上下文；调用 `out()` 时压入 `out` 的执行上下文，再调用 `inner()` 时继续压栈。函数返回后逐层出栈，回到调用者。下面的图展示了这个过程：

![&#x6267;&#x884C;&#x4E0A;&#x4E0B;&#x6587;&#x5165;&#x6808;&#x51FA;&#x6808;&#x7684;&#x5168;&#x8FC7;&#x7A0B;](../.gitbook/assets/image%20%2837%29%20%281%29.png)

我们可以发现：

1. 全局执行上下文在代码开始执行时就创建，有且只有一个，永远在执行上下文栈的栈底，浏览器窗口关闭时它才出栈。
2. 函数被调用的时候创建函数的执行上下文环境，并且入栈。
3. 只有栈顶的执行上下文才是处于活动状态的，也即只有栈顶的变量对象才会变成活动对象。

## **壹.2.2.3 变量对象（Variable Object，VO）**

**VO（变量对象）和 AO（活动对象）是早期教程的简化模型**，用来解释声明和赋值。它们不是现代 ECMAScript 规范要求引擎创建的两个实体对象；规范还涉及词法环境、变量环境等概念。

### 用简化模型理解声明的三个步骤：

1. **建立`arguments`对象**。检查当前执行上下文中的参数，建立该对象下的属性与属性值。
2. **检查当前执行上下文的函数声明，也就是使用`function`关键字声明的函数**。在变量对象中以函数名建立一个属性，属性值为指向该函数所在内存地址的引用。如果该属性之前已经存在，那么该属性将会被新的引用所覆盖。
3. **检查当前执行上下文中的变量声明，每找到一个变量声明，就在变量对象中以变量名建立一个属性，属性值为`undefined`**。**如果该变量名的属性已经存在，为了防止同名的函数被修改为`undefined`，则会直接跳过，原属性值不会被修改**。

![&#x53D8;&#x91CF;&#x5BF9;&#x8C61;&#x7684;&#x521B;&#x5EFA;&#x8FC7;&#x7A0B;](../.gitbook/assets/image%20%2833%29%20%281%29.png)

可以用以下伪代码来表示变量对象：

```text
VO={
    Arguments:{},//实参
    Param_Variable:具体值,//形参
    Function:<function reference>,//函数的引用
    Variable:undefined//其他变量
}
```

当执行上下文进入执行阶段后，变量对象会变为**活动对象**（Active Object，AO）。此时原先声明的变量会被赋值。**变量对象和活动对象都是指同一个对象，只是处于执行上下文的不同阶段**。

我们可以通过以下伪代码来表示活动对象：

```text
AO={
    Arguments:{},//实参
    Param_Variable:具体值,  //形参
    Function:<function reference>,//函数的引用
    Variable:具体值//注意，这里已经赋值了喔
}
```

### 全局执行上下文的变量对象

在浏览器普通脚本里，`var` 声明和全局对象之间存在特殊关系；但 ES Module、`let`、`const` 以及 Node.js 运行环境不能照着“全局变量对象就是 window”套用。顶层 `this` 也要看运行模式，ES Module 顶层是 `undefined`。

### 同名函数与 var 声明

```javascript
function func() {
    console.log('function func');
}
var func = "coffe";
console.log(func); //>> coffe
// 以上代码中，按三条规则，变量声明的 func 遇到函数声明的 func 应该会跳过，
// 可是为什么最后 func 的输出结果仍然是被覆盖了显示"coffe"呢？
// 那是因为三条规则仅仅适用于变量对象的创建阶段，也即执行上下文的创建阶段。
// 而 func="coffe" 是在执行上下文的执行阶段中运行的，输出结果自然会是"coffe"。
```

这种现象很容易让人费解，其实也是因为`var`声明的变量允许重名导致的，若使用关键字`let`来声明变量，就可以避免这种令人费解的情况发生。

## 壹.2.2.4 作用域链（Scope Chain）

![变量查找沿着函数定义时确定的外层作用域逐层向外](../.gitbook/assets/teaching-focus-lexical-scope.svg)

> **看图提示：** 函数里找不到变量，就向定义时的外层作用域查找；不是沿调用者的作用域查找。

### 定义

作用域链可以理解为**当前词法环境到外层环境的查找路径**。查找变量时按这条路径向外寻找；不必把它理解成引擎内部固定的“变量对象链表”。

![&#x4F5C;&#x7528;&#x57DF;&#x94FE;&#x7684;&#x56FE;&#x793A;](../.gitbook/assets/image%20%2829%29.png)

作用域链的最顶端一定是当前作用域（local scope）对应的变量对象，最底端一定是全局作用域对应的变量对象（全局VO）。

理解作用域链，可以把它想成一个蒸笼。

![&#x84B8;&#x7B3C;](../.gitbook/assets/image%20%2826%29.png)

最底下的一屉，相当于是全局作用域，它里面的蒸汽（变量和函数的可见性）可以渗透到整个蒸笼，底层之上的其他屉相当于局部作用域，这些上面屉的蒸汽只能影响更上面的屉。

作用域链可以理解为下面这种伪代码格式：

```text
{
    Scope: [
        { //当前作用域对应的VO
            实参,
            形参,
            变量,
            函数
        }, 
        { //第二个作用域对应的VO
            实参,
            形参,
            变量,
            函数
        },
        ... 
        { //全局作用域对应的VO
            变量,
            函数
        }
    ]
}
```

### 变量/函数的查找机制

变量查找从当前词法环境开始，沿**函数定义时**的外层环境逐级寻找；直到找到绑定，或查找失败。这与函数从哪里被调用没有直接关系。
