# 壹.1.2 JavaScript 未来的方向：别只盯着新语法

每隔一段时间，就有人说 JavaScript 要变天了。以前是 TypeScript 要取代 JavaScript，后来又是 WebAssembly，再后来是某个新运行时、某个新构建工具。

折腾半天，我们每天在浏览器里写的，还是 JavaScript。

这门语言当然一直在变，但我觉得更值得问的是：**变了什么，解决了什么老问题，代价又是什么？** 否则新名词背了一箩筐，真写项目还是两眼一抹黑。

## 壹.1.2.1 2026 年了，ES6 还算新东西吗？

ES6，也就是 ECMAScript 2015，当然早就不是新版本了。ECMAScript 在那之后按年度持续修订，**ECMAScript 2026 已经正式发布**。

想追最新规范，别找某个博主的“ES 最新十大神技”，直接去看 [ECMA-262 正式标准](https://ecma-international.org/publications-and-standards/standards/ecma-262/) 和 [TC39 的持续更新草案](https://tc39.es/ecma262/)。

这里有个容易混淆的地方：

- **提案：** TC39 讨论中的新功能，不等于已经成为正式标准。
- **标准：** 功能写入某年度 ECMAScript，也不代表所有旧浏览器和旧 Node.js 都支持。
- **实际可用：** 还得看目标运行环境、兼容性和构建配置。

把这三个阶段混为一谈，文章很容易写得热闹，读者拿去一运行就报错。

## 壹.1.2.2 看一个 2026 年的新标准能力

JavaScript 的浮点数加法，有时候看起来像在跟你开玩笑：

```javascript
const numbers = [1e16, 1, -1e16];
console.log(numbers.reduce((sum, n) => sum + n, 0)); // 0

if (typeof Math.sumPrecise === 'function') {
  console.log(Math.sumPrecise(numbers)); // 1
} else {
  console.log('当前环境还不支持 Math.sumPrecise');
}
```

数学上明明应该得到 1，普通依次相加却可能因为浮点精度损失得到 0。ECMAScript 2026 加入的 `Math.sumPrecise`，就是为更精确地求和提供一个标准方法。

但你看，我特意加了 `typeof` 判断。**标准发布是一回事，用户手里的浏览器支持又是另一回事。** 要不要直接用，先查兼容性；如果你的业务涉及金额，还得考虑整数最小货币单位、十进制计算库等更完整的方案，不能指望一个求和方法治好全部财务问题。

## 壹.1.2.3 TypeScript 会不会吃掉 JavaScript？

这两个名字经常被放在一起吵架，好像只能活一个。

TypeScript 帮你在开发阶段发现一部分类型错误，让大项目更容易维护；最后运行在浏览器里的仍然通常是 JavaScript。**类型检查通过，也不等于接口返回值真的符合你的类型声明。**

```typescript
type User = { id: number; name: string };

async function getUser(): Promise<User> {
  const res = await fetch('/api/user');
  return await res.json(); // TS 不会替你验证服务器真的返回了 User
}
```

这段代码里，`Promise<User>` 更像一份承诺，不是运行时的安检。真要防止后端返回乱七八糟的数据，还需要运行时校验。

至于 JavaScript 原生类型注解的讨论，**看清楚提案与正式标准的区别**。不能因为在新闻里见过“正在推进”，就告诉读者“浏览器已经原生支持完整 TypeScript”。

## 壹.1.2.4 Node、Deno、Bun：都能跑 JS，为什么还要选？

浏览器之外，JavaScript 已经有不止一种运行环境。Node.js、Deno、Bun 都能运行 JavaScript，但它们的 API、兼容性、权限机制、工具链和部署生态不完全一样。

我判断一个运行时，不会先问谁的跑分海报做得漂亮，而是看这几件事：已有项目能否跑起来、依赖库支不支持、线上出问题怎么排查、团队愿不愿意维护。

**跑得快是优点，跑得稳、出了问题有人会修，才算真正能用。**

## 壹.1.2.5 工具链也在变，别把工具当信仰

Vite、Webpack 以及其他构建工具，解决的是项目开发与构建的问题，不是 JavaScript 语言本身。

新项目可以优先评估更适合当前需求的方案，旧项目也不用听见“新工具更快”就立刻推倒重来。迁移之前看一眼打包产物、构建耗时、插件兼容性和团队的人力成本。

工具的目的，是让你更容易交付可靠的软件。要是换工具花了一个月，业务却一点没改善，这次升级到底图什么？

## 壹.1.2.6 AI 时代，JavaScript 工程师该把精力放在哪？

今天 AI 能写一大段页面、组件和接口代码。看起来程序员可以少背很多语法，事实也确实如此。但麻烦跟着来了：AI 写出来的代码，**编译通过不等于逻辑正确，页面能打开不等于安全可靠**。

我建议重点练三样东西：

1. **读懂底层原理：** 作用域、异步、事件循环、网络、浏览器渲染，出了问题才有判断力。
2. **验证代码：** 会写测试、看性能数据、查安全边界、判断浏览器兼容性。
3. **做工程选择：** 知道什么时候用框架、什么时候写原生代码、什么时候不该引入新依赖。

AI 可以替你多打些字，但它不会自动替整个团队承担线上故障。**谁能把需求、验证和交付串起来，谁就更有价值。**

## 壹.1.2.7 不猜未来，先看变化背后的原因

前端这些年，我觉得有件事挺有意思：每隔一阵子，大家就说旧工具不行了，新东西要统一天下。结果呢？旧工具还在跑，新工具又有了新毛病。

所以我看 JavaScript 的发展，更想弄清楚旧方案究竟哪里难用，新东西解决了多少问题，又带来了哪些麻烦。这个比死记年度版本号实在。

如果你每次都把“新版本有什么”当成学习重点，知识会像无底洞。更可靠的办法是追问：**旧方案哪里让人难受，新方案准备解决什么问题，又带来什么代价？**

例如：

- **ES Modules：** 以前模块组织和依赖管理缺乏标准化语言机制；有了标准模块后，浏览器和运行时可以更明确地理解依赖关系。
- **TypeScript：** 大团队里动态类型造成的部分低级错误，能在编译阶段被提前发现。但类型不等于运行时验证，也不能代替测试。
- **Vite 一类开发工具：** 不少传统构建流程在大项目的开发启动与热更新上耗时明显，新工具尝试优化开发反馈路径。生产构建仍需要处理资源转换和优化。
- **WebAssembly：** 让 Web 可以运行用其他语言编译出的模块，适合部分计算密集任务，但不是“全面取代 JavaScript”。

## 壹.1.2.8 面试官问“JavaScript未来会怎样”，怎么回答？

假如面试官问我“JavaScript 将来会怎样”，我不会把十几个还没落地的提案念一遍。语言标准当然重要，可对于每天写项目的程序员，我觉得下面三个方向更值得看：

1. **开发效率：** 模块、工具链、类型检查和开发体验持续改进。
2. **运行平台：** 浏览器之外的服务器、桌面与边缘环境不断发展。
3. **工程可靠性：** 安全、性能、可维护性、可观察性越来越重要。

举个例子：同一个需求可以用浏览器 JS、Node.js、Deno 或其他运行时实现，但底层权限、API、部署环境和生态支持不一样。不能因为“都是 JavaScript”就推导出“所有环境都能运行同一段代码”。

## 壹.1.2.9 一个实际练习

挑一个 3 年以上的前端项目，尝试只回答四个问题：哪些痛点是语言本身造成的？哪些是构建工具造成的？哪些是业务复杂度造成的？哪些可以通过团队规范解决？

把问题归类后，再评估是否要升级依赖、重构架构、采用新框架。**真正有价值的技术视野，不是永远追着最新发布会跑，而是看得出哪些变化对业务有用。**

本章提到的具体标准提案状态与工具版本会变化，正式选型应再核对当时的官方文档。

我宁愿你把一个老项目的技术问题说清楚，也不愿你背了几十个新 API，真遇到 Bug 却不知道从哪里下手。
