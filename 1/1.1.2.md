# 壹.1.2 JavaScript 未来的方向：别只盯着新语法

JavaScript 的新技术一茬接一茬。学之前先问三个问题：**解决什么问题、付出什么代价、我的项目用不用得上？**

## 壹.1.2.1 2026 年了，ES6 还算新东西吗？

ES6，也就是 ECMAScript 2015，当然早就不是新版本了。ECMAScript 在那之后按年度持续修订，**ECMAScript 2026 已经正式发布**。

查新特性直接看 [ECMA-262 正式标准](https://ecma-international.org/publications-and-standards/standards/ecma-262/) 和 [TC39 的持续更新草案](https://tc39.es/ecma262/)。

这里有个容易混淆的地方：

- **提案：** TC39 讨论中的新功能，不等于已经成为正式标准。
- **标准：** 功能写入某年度 ECMAScript，也不代表所有旧浏览器和旧 Node.js 都支持。
- **实际可用：** 还得看目标运行环境、兼容性和构建配置。

## 壹.1.2.2 看一个 2026 年的新标准能力

先看浮点数求和的例子：

```javascript
const numbers = [1e16, 1, -1e16];
console.log(numbers.reduce((sum, n) => sum + n, 0)); // 0

if (typeof Math.sumPrecise === 'function') {
  console.log(Math.sumPrecise(numbers)); // 1
} else {
  console.log('当前环境还不支持 Math.sumPrecise');
}
```

数学上明明应该得到 1，普通依次相加却可能因为浮点精度损失得到 0。ECMAScript 2026 加入的 `Math.sumPrecise`，就是为更精确地求和提供一个标准方法。

使用前检查目标环境是否支持。金额运算还需要考虑整数最小货币单位或十进制计算库，`Math.sumPrecise` 不能解决所有精度问题。

## 壹.1.2.3 TypeScript 会不会吃掉 JavaScript？

TypeScript 帮你在开发阶段发现一部分类型错误，让大项目更容易维护；最后运行在浏览器里的仍然通常是 JavaScript。**类型检查通过，也不等于接口返回值真的符合你的类型声明。**

```typescript
type User = { id: number; name: string };

async function getUser(): Promise<User> {
  const res = await fetch('/api/user');
  return await res.json(); // TS 不会替你验证服务器真的返回了 User
}
```

`Promise<User>` 是类型声明，不会验证接口响应。关键数据仍要做运行时校验。

至于 JavaScript 原生类型注解的讨论，**看清楚提案与正式标准的区别**。不能因为在新闻里见过“正在推进”，就告诉读者“浏览器已经原生支持完整 TypeScript”。

## 壹.1.2.4 Node、Deno、Bun：都能跑 JS，为什么还要选？

浏览器之外，JavaScript 已经有不止一种运行环境。Node.js、Deno、Bun 都能运行 JavaScript，但它们的 API、兼容性、权限机制、工具链和部署生态不完全一样。

选择运行时，重点检查依赖兼容性、部署环境、调试手段和团队维护能力，不要只看跑分。

## 壹.1.2.5 工具链也在变，别把工具当信仰

Vite、Webpack 以及其他构建工具，解决的是项目开发与构建的问题，不是 JavaScript 语言本身。

新项目可以优先评估更适合当前需求的方案，旧项目也不用听见“新工具更快”就立刻推倒重来。迁移之前看一眼打包产物、构建耗时、插件兼容性和团队的人力成本。

## 壹.1.2.6 AI 时代，JavaScript 工程师该把精力放在哪？

AI 可以生成组件和接口代码，但**编译通过不等于逻辑正确，页面能打开不等于安全可靠**。

我建议重点练三样东西：

1. **读懂底层原理：** 作用域、异步、事件循环、网络、浏览器渲染，出了问题才有判断力。
2. **验证代码：** 会写测试、看性能数据、查安全边界、判断浏览器兼容性。
3. **做工程选择：** 知道什么时候用框架、什么时候写原生代码、什么时候不该引入新依赖。

## 壹.1.2.7 动手判断一次技术升级

挑一个维护了三年以上的项目，查清问题来自语言、构建工具还是业务本身，再决定要不要升级。尤其别把 WebAssembly 当成 JavaScript 的替代品：它适合某些计算密集型任务，普通页面逻辑仍要依赖 JavaScript。

提案状态与运行环境支持随时可能变化，选型时以官方标准和目标环境的测试结果为准。
