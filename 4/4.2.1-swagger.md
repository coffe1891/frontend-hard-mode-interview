# 肆.2.1 使用 Swagger / OpenAPI 管理前后端接口

前后端联调最常见的混乱，并不是“接口写不出来”，而是**字段名、类型、错误码、鉴权方式和修改记录没有统一约定**。OpenAPI 可以把这些约定放进一份机器和人都能阅读的文档。

## 01. 先分清三个名字

- **OpenAPI Specification（OAS）**：描述 HTTP API 的开放规范。
- **Swagger UI**：根据 OpenAPI 文档展示可交互的接口页面。
- **Swagger Editor 等工具**：帮助编写、检查文档。Swagger 是一套工具生态的名字，不应把它与规范本身混为一谈。

## 02. 一个最小的 OpenAPI 示例

```yaml
openapi: 3.1.0
info:
  title: 示例订单接口
  version: 1.0.0
paths:
  /orders/{id}:
    get:
      summary: 按编号查询订单
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: string
      responses:
        '200':
          description: 成功
          content:
            application/json:
              schema:
                type: object
                required: [id, status]
                properties:
                  id: { type: string }
                  status: { type: string, enum: [pending, paid] }
        '404':
          description: 订单不存在
```

注意 `200` 只表达 HTTP 状态，业务错误码可以在响应体中另行定义；必须明确两者各自的含义。接口文档也不应把生产密钥直接放进示例。

## 03. 如何让文档不变成摆设？

1. 以规范为契约，接口修改与文档修改进入同一次代码评审。
2. 在 CI 中做规范校验，检查缺失的必填字段和破坏性变更。
3. 使用 Mock、代码生成或契约测试辅助联调，但不要假设生成客户端就能保证服务端实现正确。
4. 约定错误响应结构、分页、时间格式、鉴权和版本策略。

## 04. 面试高频问题

**OpenAPI 能否替代接口测试？** 不能。文档表达“期望怎么做”，测试验证“实际是否这么做”。两者结合，才可能减少“文档明明是对的，线上行为却不一样”。
