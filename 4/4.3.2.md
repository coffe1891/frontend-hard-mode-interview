# 肆.3.2 适用于前端开发者的 20 个 VS Code 插件

每隔一阵子，总能看到一份“前端必装的二十个插件”清单。有人见一个装一个，最后 VS Code 启动慢了，格式化还互相打架。

我觉得清单可以参考，但别把插件数量当成绩。下面按用途列出常见扩展，装之前记得查发布者和官方 Marketplace 页面，别随便从聊天群下载不明来源的 VSIX。

## 01. 安装顺序应该怎样？

我的建议是先装团队确实依赖的工具：**语言服务 → ESLint/Formatter → Git → 测试 → 按需辅助功能**。例如只写 React 的项目，没必要同时装多个 Vue 语言服务；没有用 Tailwind，也不用安装相关插件。

## 02. ESLint 与 Prettier 冲突怎么办？

ESLint 偏向代码质量和部分风格检查，Prettier 专注格式化。应由团队明确二者边界，配置兼容策略，而不是让两个工具在保存时相互改来改去。

## 03. 插件也是供应链软件

安装前核对**发布者、安装量、最近更新、权限与仓库来源**，不要只看名字。不要随意安装来源不明、索取大量权限的扩展；公司项目尤其要注意工作区信任与凭据泄漏。

## 04. 安装了 20 个就能提高效率吗？

未必。有的扩展功能重叠，可能带来更高的资源占用。优先掌握编辑器自带的符号跳转、重构、断点和 Git 功能，扩展只用来填补真实短板。

工具是用来帮你干活的。要是为了维护二十个插件，天天花时间解决插件冲突，那就本末倒置了。

## 05. 别只收藏清单：手把手配置一次ESLint与Prettier

假设两个同事同时改一个 JS 文件，一个用单引号，一个用双引号，一个加分号，一个不加。Git diff 被格式变化刷满，真正改了什么业务代码，反倒看不清了。

这个时候，把 ESLint、Prettier 和团队配置弄一致，比再安装十个插件有用。

正确办法是**把规范写进项目，而不是指望大家的编辑器恰好设置一样**。

先安装项目依赖（具体版本与配置格式按项目的 ESLint/Prettier 版本选择）：

```bash
npm install -D eslint prettier
```

Prettier 示例配置 `.prettierrc.json`：

```json
{
  "singleQuote": true,
  "semi": true,
  "printWidth": 100
}
```

`package.json` 中声明脚本（以下是片段）：

```json
{
  "scripts": {
    "format": "prettier --write .",
    "format:check": "prettier --check ."
  }
}
```

运行 `npm run format:check`，就能检查格式是否符合团队约定。注意：`prettier --write .` 会遍历项目，真实工程应通过 `.prettierignore` 排除构建产物、依赖目录和不需要修改的文件。

ESLint 的作用和 Prettier 不一样。前者负责报告潜在代码问题，例如未使用的变量、某些不安全的写法；后者主要统一格式。二者可以配合，但要避免重复互相冲突的规则。

## 06. 一个真实的插件冲突怎么排查？

现象：保存文件后，缩进先变成 2 个空格，又被改成 4 个；或者 Vue 模板格式一会儿正常，一会儿乱跳。

不要见到异常就继续安装插件。按这个顺序排查：

1. 打开 `Format Document With...`，看当前使用哪个格式化器。
2. 查看工作区 `settings.json` 是否配置了多个默认格式化器。
3. 暂时禁用可疑扩展，确认是否由两个插件竞争修改文件。
4. 在命令行运行项目内的 Prettier，观察结果是否与编辑器一致。
5. 把团队确认的方案固定到仓库，减少“我电脑正常”的情况。

## 07. 插件越多，排查成本越高

还有一件事我得提醒：编辑器插件不是无害的小挂件。能读取工作区的插件，至少有机会接触仓库里的文件。安装前看看发布者、更新记录、权限和信誉，别什么都往生产项目里装。

尤其不要从聊天群随便下载不明来源的 VSIX 安装包，然后把含有生产密钥的仓库全部交给它扫描。**编辑器插件也是要信任的第三方程序。**

## 08. 练习题

挑一个真实项目，完成以下三步：统一格式配置、在 CI 中检查格式、随机修改三处文件后核对 Git diff。

做完这三个动作，远比背下二十个插件名字更能提升团队协作效率。
