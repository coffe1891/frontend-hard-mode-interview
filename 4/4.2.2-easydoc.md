# 肆.2.2 Easydoc等在线接口文档工具，应该怎么选？

项目刚开始时，前端问接口是什么，后端在聊天群里发一个 JSON 截图；过两天字段改了，文档没有更新，测试同事还在用旧版本。

在线接口文档平台能让大家在一个地方讨论请求、响应、示例和修改记录。但**平台名字不重要，能不能让文档一直可信才重要**。

## 01. 先看团队真正在痛什么

如果团队只有两位工程师、四个接口，仓库里一份简洁的 Markdown 文档可能足够。若十几个项目组、多个环境、多个接口版本并行维护，就需要更强的协作能力。

评估 Easydoc 或其他接口平台时，别先问“界面漂不漂亮”，先问：

- 能不能导入导出 OpenAPI 等通用格式？
- 能不能管理开发、测试、预发布等环境地址？
- 能不能对字段变化留审计记录？
- 能不能让测试人员在不获取生产密钥的情况下调试？
- 停止使用这个平台后，接口合同能不能完整迁移出来？

## 02. 一次真实的前后端联调怎么做？

拿“新增收货地址”接口举例。评审时就先约定：

```text
POST /api/addresses
Content-Type: application/json

请求：
{ "name": "小王", "phone": "13800000000", "city": "上海" }

成功（201）：
{ "id": 123, "name": "小王", "city": "上海" }

验证失败（422）：
{ "code": "INVALID_PHONE", "message": "手机号格式错误" }
```

这里是教学示例，手机号、地址和错误码需要按实际业务要求定义。

前端根据合同写表单和错误提示，后端按合同实现，测试根据合同构造用例。等实现完成后，再核验真实返回数据与文档是否一致。

## 03. 用Mock先把页面做出来

很多团队的痛点是后端接口没写完，前端就停工了。只要合同先定好，前端就可以做一个临时 Mock：

```javascript
async function fakeCreateAddress(data) {
  if (!data.phone) {
    return { ok: false, error: { code: 'INVALID_PHONE' } };
  }
  return { ok: true, data: { id: 123, ...data } };
}

fakeCreateAddress({ name: '小王', phone: '', city: '上海' })
  .then(console.log);
```

Mock 的目的是让前端先完成交互验证，而不是永久替代真实接口测试。联调阶段仍要检查权限、边界值、错误响应和环境差异。

## 04. 线上工具最容易忽略的安全问题

绝不能把生产管理员 Token、数据库密码或包含真实用户隐私的数据直接填入共享的接口文档平台。测试环境优先使用专门的低权限凭据和匿名数据。

另外，平台如果不能导出通用格式，你可能会形成严重的供应商锁定。换工具时，几百个接口文档只能手工搬家，这个成本比订阅费更吓人。

## 05. 什么时候选择Git仓库里的OpenAPI？

如果团队希望把 API 变更和代码评审绑在一起，使用仓库内的 OpenAPI 文件，配合 CI 检查和可视化工具，往往是稳妥路线。在线平台也可以作为协作界面，但要确定谁是唯一可信的来源，避免维护两套互相矛盾的合同。

## 06. 面试怎么回答？

别回答“我用过某某平台，感觉挺好”。更有价值的答案是：**接口文档如何版本管理、如何确保实现一致、如何处理不兼容变更、如何防止密钥泄漏**。工具只是把流程落地的手段。
