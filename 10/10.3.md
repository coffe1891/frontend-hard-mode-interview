# 拾.3 AI 时代，前端工程师还有出路吗？我给你五条能走的路

> **更新日期：2026 年 11 月 22 日。** 文中引用了 GitHub、Stack Overflow、DORA 等官方资料。已经发生的事与我对 2027 年的判断会分别说明。技术演进不等于就业市场预测，任何路线都不保证涨薪或转岗。

我写《前端内参》时，一直有个想法：**成为一个好的程序员，比学会几个热门框架更重要。**

可到了 2026 年，前端工程师遇到了一个新问题。

以前产品经理让你做一个管理后台，你写组件、接接口、调样式，忙上好几天。现在有人给 AI 说几句话，可能很快就做出了一个像模像样的页面。

这时候，恐怕不少朋友心里都要咯噔一下：

**AI 连页面都能写了，我们这些前端工程师，以后靠什么吃饭？**

我先说自己的判断：**前端还有出路，但如果你的全部本事就是照着设计稿拼页面、照着教程调 API，日子恐怕会越来越被动。**

这不是说前端已经大规模失业了。不同城市、行业和公司，招聘情况完全不同。我的意思是：重复写代码的成本在下降，我们不能还把“敲得快”当成唯一优势。

下面不喊口号。我把自己认为值得走的五条路，还有一份 90 天计划，都讲清楚。

## 01. AI 到底已经能干到什么程度了？

先别拿两三年前只能帮你补全一行代码的 AI，去想象今天的编程工具。

**已确认的事实：** GitHub 官方文档介绍，Copilot 现在可以研究代码仓库、制定方案、修改文件、运行工具，准备代码变更供人审查。它已经不只是自动补全。

2026 年 GitHub 的 Octoverse 报告提到：在 **Copilot 月活跃用户** 中，使用代理式功能的比例达到 **55%**，一年前是 35%。这里的分母很重要，不是说全球 55% 的程序员都在使用 AI 代理。

Stack Overflow 的 2026 开发者调查又给出了另一面：收到 AI 生成的开发答案之后，约 **76%** 的受访者会在本地运行验证，约 **64%** 会对照现有代码库，约 **53%** 会检查测试或安全影响；只有不到 10% 会直接原样采用。

你看，AI 越来越能干了，但认真做项目的人，并没有因此放弃检查代码。

想象一个订单页面。你让 AI 加个“取消订单”按钮，它可能很快就写好了：按钮、点击事件、接口请求、成功提示，一样不缺。

但我问你：

- 已经付款的订单，还能取消吗？
- 用户 A 能不能拿用户 B 的订单号去调用接口？
- 用户连续点三次，会不会发出三次请求？
- 请求超时了，服务器其实取消成功了，前端应该怎么处理？
- 取消和发货两个请求同时到了服务器，到底谁说了算？

**写出一个按钮，与把取消订单功能做对，是两件完全不同的事。**

以前敲代码很费时间，这些真正麻烦的问题容易被代码量掩盖。现在 AI 把重复劳动做快了，反倒让我们看清：软件开发里究竟什么东西最值钱。

## 02. 哪些工作可能越来越不值钱？

我认为有三类工作，会遇到越来越大的价格压力。但下面是**个人判断**，不是已经验证的岗位淘汰比例。

**第一，照着设计稿重复拼静态页面。**

普通宣传页、表单、列表、弹窗，只要需求清楚，AI 已经能帮忙生成不少代码。客户和企业将来是否还愿意为每一段重复劳动付同样的价钱？我觉得很难乐观。

**第二，只会照着教程调用框架 API。**

`useState` 怎么写，Vue 的组件怎么拆，一个表格库怎么配置。AI 查得快，写得也快。

如果你唯一的优势就是记住了这些 API 的参数，那可真有点危险。

**第三，出了问题只会复制粘贴答案。**

碰到报错，把红字扔给 AI；得到一段代码，贴进去；不报错就算解决。

但如果线上出了问题，谁改坏了状态、为什么权限失效、为什么页面卡顿，你一句也解释不出来。AI 越方便，这种“不懂也能改”的习惯越容易把项目弄乱。

**我不是反对大家写页面。我反对的是，工作了好几年，能力却始终停留在“只会写页面”。**

## 03. 第一条路：向全栈走，成为能独立交付产品的人

如果你已经熟悉 React 或 Vue，我认为这是很多业务型前端工程师最值得优先考虑的一条路。

先说明白，全栈不是让你一口气学完 Java、Go、Rust、Kubernetes，然后再背三十种数据库。

那不是转型，是给自己加刑。

你先把一个真实需求，从浏览器做到服务端、数据库、测试和部署，已经是相当有价值的一步。

拿订单管理系统来说：

1. **前端**：登录、列表、筛选、订单详情、取消按钮、错误提示。
2. **后端**：订单 API、权限校验、业务状态判断。
3. **数据库**：订单表、用户表、基础索引、事务与必要的并发处理。
4. **部署**：环境变量、日志、监控、发布和回滚。
5. **测试**：不光测试能成功，还要测无权限、重复提交、网络错误等边界。

注意，**前端隐藏一个按钮不算权限控制。** 用户完全可以绕过页面直接请求接口。真正的权限和订单状态，必须在可信的服务端检查。并发修改还可能需要事务、条件更新或幂等设计。

原来你只能说“我把页面做出来了”。学完这些，你可以说“我把整套功能做完了，而且知道出错时怎么排查”。

**适合的人：** 已有一定前端经验、经常做业务项目，希望提升独立交付能力。

**怎么开始：** 熟悉 TypeScript，就先沿着 Node.js 加关系型数据库走。不必一下学三个后端框架。项目做完，再根据遇到的问题补课。

## 04. 第二条路：继续做前端，但要钻得足够深

有人不喜欢写后端，就喜欢琢磨浏览器、渲染和性能。

可以。这也是一条路。

前端还有很多活，不是让 AI 拼几个组件就能自动解决的：复杂性能、可访问性、安全、浏览器兼容、大型系统迁移，以及线上问题排查。

比如一个页面展示两万条商品，用户输入搜索词，页面就卡住。

你怎么办？

先骂 React？先装个优化插件？还是直接让 AI 给所有组件加 `memo`？

我觉得应该先打开开发者工具查：

- 是不是一次性渲染了太多 DOM？
- 是不是每敲一个字，就重新计算了整张表？
- 是不是长任务占住主线程？
- 是不是布局不断变化，浏览器反复重排？
- 是请求慢，还是脚本慢？

你能找到原因，再通过可复现的测试证明修复有效，这比“精通 React 性能优化”八个字有说服力多了。

**建议选一个方向先做深**：性能工程、前端安全、可访问性、复杂组件基础设施、大型项目迁移。不要把“所有方向都精通”当成目标。

**适合的人：** 已有较深前端经验，喜欢研究技术原理，又不想把职业重心改成后端开发。

**怎么开始：** 从做过的真实项目里找一个问题，保存“现象—定位—修改—测量”的完整记录。没有真实数据，就用有代表性的测试数据，但别假装那是线上结果。

## 05. 第三条路：做 AI 应用工程师，别只会套一层聊天框

现在不少朋友一听 AI 应用，就想到网页里放一个聊天窗口，再调个模型 API。

说实话，这个门槛也在下降。

真正值得做的是：**让 AI 在一个具体业务里，安全、稳定地帮用户解决问题。**

比如做企业内部的订单知识助手。用户问：“为什么我的订单没有退款？”

麻烦在什么地方？

系统得知道这个用户是谁、能看哪些订单；从订单系统和支付系统取到正确记录；模型不能编造退款状态；说不知道的时候就得说不知道；涉及真正退款的操作，必须有权限和确认机制。

这里面，前端工程师的优势其实挺明显：我们懂交互、状态、异步请求和用户体验。

但还要补上数据、服务端、模型工具调用、评测、日志和费用控制。

尤其是权限。OWASP 专门讨论过 **Prompt Injection（提示词注入）**：AI 读取到的网页、文档、仓库内容，可能夹着恶意指令。能读不代表可信，更不能让模型凭一段不可信文字就获得支付、发邮件等高风险操作权限。

**适合的人：** 对 AI 产品有兴趣，愿意补服务端和数据能力的前端工程师。

**怎么开始：** 做一个范围很小的 AI 工具，例如“只回答某份产品手册的问题”，要求能展示资料来源、拒绝越权访问、记录错误样例。别一上来就要做“超级智能体”。

## 06. 第四条路：学会带着 AI 干活

我觉得未来的高级工程师，会越来越需要两种能力：

**自己知道什么是对的；还知道怎样把适合的任务交给 AI。**

但我不太喜欢“只要会提示词就能当程序员”这种说法。提示词写得漂亮，最后代码跑不了，算什么本事？

以前面说的订单功能为例。

你如果只是说：

> 帮我加个取消订单按钮，做漂亮一点。

AI 把按钮写出来，其实就算回应了你的要求。可你真要上线，还远远不够。

不如把任务写清楚：

~~~text
任务：给订单详情页添加“取消订单”功能。

业务规则：
1. 只有订单所有者可以取消自己的订单。
2. 只有 pending 状态允许取消。
3. 服务端必须重新验证身份、权限与最新订单状态。
4. 重复请求和并发修改必须有明确处理策略。
5. 不改动现有付款、发货和退款规则。

验收：
1. 增加允许取消和拒绝取消的测试。
2. 覆盖接口失败、无权限和重复点击。
3. 检查窄屏、键盘操作和错误提示。
4. 列出修改的文件、实际运行的测试与未解决的风险。
5. 不读取、输出或提交真实密钥。
~~~

这也不是什么万能提示词，AI 依然可能犯错。

真正的流程应该是：

**你定义需求和边界 → AI 提方案 → 在独立分支修改 → 运行测试 → 人工审查差异 → 决定是否发布。**

检查什么？

AI 有没有乱改无关文件？有没有把服务端校验偷偷移到前端？有没有乱加依赖？测试到底跑没跑？错误能不能回滚？

GitHub 官方对编程代理也强调人工审核，并为代理的权限、执行和审计设计了保护机制。这些不是多此一举。

**我的看法是：AI 应该是一个动作很快、但需要严格验收的协作者。不能把它当成从不犯错的技术总监。**

**适合的人：** 所有已有编程基础的人，尤其是技术负责人、需要代码评审和协作的人。

## 07. 第五条路：懂一门生意，自己做产品

如果你对某个行业特别熟悉，还有另外一条路：用前端、后端和 AI，做一款小产品。

比如你熟悉电商，知道小商家每天都要人工整理大量售后工单；或者你熟悉教育，知道老师整理教学材料很费时间。

过去开发软件成本高。现在代码可以生成得更快，试错门槛可能降低。

但这里我得泼点冷水：

**会做产品，不代表有人愿意用；有人愿意用，也不代表有人愿意付钱。**

我建议先找真实用户，确认他们每天为什么烦、目前怎么解决、愿意为解决问题付出什么。再做一个最小版本。

譬如先做个售后工单分类工具，只帮商家把待处理订单整理出来，让人审核结果。记录准确率、节省的时间和实际使用情况，别急着让 AI 自己决定退款。

如果用户根本不用，功能做得再炫也没用。

**适合的人：** 熟悉行业、能接触用户、有长期独立经营意愿的人。

**怎么开始：** 先访谈真实用户，再做小产品，随后验证使用和收费。程序员习惯先写代码，这条路反而要克制一下。

## 08. 五条路怎么选？给不同阶段的朋友一个建议

有些朋友看到这里可能又要焦虑了：全栈也要学，AI 也要学，性能还要学，那不是比以前更累？

所以我不建议你五条一起走。

| 目前的情况 | 优先路线 | 三个月后争取拿出的东西 |
| --- | --- | --- |
| 做页面熟练，但没独立交付过完整应用 | 全栈交付 | 一个有 API、权限、数据库、测试和部署的小产品 |
| 前端经验较深，喜欢钻技术 | 性能、安全或架构专长 | 一份有测量、定位和修复结果的技术案例 |
| 想进入 AI 产品开发 | AI 应用工程 | 一个有资料来源、权限控制和错误评测的 AI 小工具 |
| 已经在带项目、做技术评审 | AI 协作与工程流程 | 一套能复用的任务说明、测试、审核与回滚流程 |
| 熟悉具体行业、能接触真实客户 | 垂直产品 | 一个有人持续使用、价值能被验证的最小产品 |

工作多年的工程师，我还想特别说两句。

有些人干了十几年，便开始担心年龄，转头跟刚毕业的人比谁切页面更快、谁肯熬夜更多。

我觉得这比赛选错了。

你见过的线上事故、理解的复杂业务、积累的沟通经验，本来就是优势。补上新工具，把这些优势发挥出来，总比把自己重新练成一个“敲代码更快的初级工程师”划算。

刚入行的朋友也别因此放弃基础。代码能生成是一回事，自己能不能判断它为什么错，是另一回事。

## 09. 给你一份能动手做的 90 天计划

大道理讲完了，来点实在的。

下面按**已经掌握 JavaScript 基础、每周可以投入大约 6—10 小时**设计。基础薄弱或工作繁忙，就把周期拉长。这不是 90 天后一定能转岗的保证。

我们只做**一个**项目：小型订单管理系统。

### 第 1—15 天：把前端基础和开发环境补齐

选熟悉的 React 或 Vue，完成订单列表、搜索、筛选、详情与基础登录界面。

同时复习 TypeScript、异步请求、错误处理、Git 和基本测试。

**交付物：** 一个别人照着 README 也能在本机跑起来的项目。

### 第 16—30 天：补上 API 和数据库

用 Node.js 或其他熟悉的服务端框架实现订单 API，接一个关系型数据库。

别只写成功路径。用户 A 不能读写用户 B 的订单，这种权限规则必须由服务端执行。

**交付物：** 前后端联通，有订单接口、数据库迁移说明和基本的接口测试。

### 第 31—45 天：专门练异常和边界

模拟五件事：

1. 已支付订单不能当成待支付订单取消。
2. 用户连续点三次取消按钮。
3. 前端超时，但服务端实际处理成功。
4. 两个请求同时修改订单状态。
5. 用户试图读取或修改别人的订单。

有些问题需要幂等、事务或条件更新来处理。光禁用按钮可挡不住恶意请求。

**交付物：** 一份异常场景测试清单，每一项有明确预期。

### 第 46—60 天：做性能和上线演练

打开 Chrome DevTools 的 Performance 面板，定位一次可重复的卡顿。用同样设备、数据量和操作步骤，比较修改前后。

把项目部署到测试环境，配置日志、环境变量、简单监控和回滚办法。

**交付物：** 一份可复现的性能记录和一个可以访问的测试环境。

### 第 61—75 天：真正让 AI 参与开发

交给 AI 一个低风险任务，比如增加筛选条件或导出 CSV。

先写任务说明和验收标准，让 AI 在分支上修改，要求列出改了什么、测了什么、还有什么风险。你自己检查差异和测试结果。

**交付物：** 一次完整的“任务 → AI 修改 → 检查 → 测试 → 合并”的过程记录。

### 第 76—90 天：整理成别人看得懂的作品

把项目放到 GitHub。至少写清楚：

- 怎么运行，怎么体验；
- 为什么这样设计权限和状态；
- 关键测试怎么跑；
- 解决过什么性能或业务问题；
- AI 参与了哪些工作，你怎样验收；
- 还有哪些问题没有解决。

到这一步，面试时你就不必只是说“我会 React、Vue、TypeScript”。

你可以打开仓库，给别人讲清楚：我怎样把一个需求从页面做到服务端，怎样处理错误，怎样测试，又怎样用 AI 提高效率。

**我觉得这比堆一屏技能名词，有用得多。**

## 10. 怎么证明自己真的在进步？

不要拿“AI 替我写了一万行代码”当成绩。

我更愿意看下面四件事：

**一、能不能独立交付？** 原来只懂页面，现在能不能考虑 API、权限、数据和发布？

**二、返工是不是少了？** 代码写得很快，但改 Bug 改三天，效率就得重新算。

**三、关键功能有没有验证？** 登录、授权、订单状态这些地方，不是点两下能跑就完事。

**四、出了问题你能不能讲明白？** 生成的代码你读不懂，一出事就继续把报错贴给 AI，那还谈不上掌握技术。

DORA 2026 年的分析也提醒我们：AI 可以加快初始代码生成，但省下的时间可能重新花在审核和验证上。更高的 AI 使用率，并不自动等于更稳定的软件交付。

所以我觉得，**真正的效率不是代码生成得多快，而是正确的软件多久能交付出去。**

## 11. 这五个坑，最好别踩

**一，天天追新工具。** 一周换三次编辑器，模型名字背了一大串，项目倒是一个没完成。那不是学习，是忙着折腾。

**二，以为 AI 会写代码，自己就不用懂原理。** JavaScript 异步、浏览器渲染、HTTP、数据库、权限，这些知识没过时。

**三，什么都学，什么都学不深。** 先选一条路线。做项目遇到问题，再补真正缺的东西。

**四，把生产密钥和真实客户数据随便交给 AI。** 工具权限、隐私和公司政策都要认真对待。仓库和网页里的内容也不能天然信任。

**五，AI 能开发产品，就以为创业一定成功。** 软件开发变快，只能说明试验可以做得更快。真正的需求、用户和付费，仍得自己去找。

## 12. 我对 2027 年有三个判断

下面全是**个人预测**，不是已经发生的就业事实。

**第一个判断：重复性页面开发的溢价还会继续受到挤压。**

怎么验证？去看真实岗位和项目报价，比较企业是不是越来越在意业务理解、测试和完整交付，而不只看写组件的速度。不同地区的情况可能差别很大。

**第二个判断：懂业务、懂系统、懂验收 AI 代码的人，会更有主动权。**

怎么验证？看岗位要求和团队实际流程，有没有越来越重视系统设计、权限、安全、评审和 AI 协作成果。

**第三个判断：好程序员的标准不会消失，但会更严格。**

以前你要写好代码；现在还得懂哪些能交给 AI、怎么验收、出了问题怎么回滚。

怎么验证？别只看代码量，比较真实项目在引入 AI 前后的交付周期、缺陷、返工率与维护成本。

## 写在最后

我在[《成为一个好的程序员远比找份好工作重要》](10.1.md)里谈过，程序员不应该只面向工作去编程，更应该面向成为一个更好的程序员去编程。

到了 AI 时代，我依然这么想。

如果我们每天只关心“怎样把这一段代码敲出来”，那 AI 越强，我们就越容易焦虑。毕竟和机器比生成代码的速度，这比赛实在不划算。

可如果我们关心的是怎样把业务弄明白，怎样让系统安全、稳定、好用，事情就不一样了。

AI 可以帮你写代码、查资料、跑测试、改 Bug。

**但你至少要有本事判断：它做得对不对。**

前端工程师的出路在哪里？

**在浏览器之外多走一步，在技术深处多钻一层，在真实业务里多解决一个问题。**

比起每天担心 AI 什么时候取代自己，我更愿意把时间花在下一个能经得起检验的项目上。
