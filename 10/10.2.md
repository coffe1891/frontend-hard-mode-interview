# 拾.2 2026 前端技术展望：走向 2027 年，什么值得学？

> **本文更新于 2026 年 11 月 22 日。** 文中谈到的框架版本、工具发布，依据官方资料核对；谈到 2027 年会怎样，那是我的判断，不是已经发生的事实。参考资料都放在文末。

前端这行，最不缺的就是新东西。

昨天还在讨论 Vue 和 React 谁更好，今天来了 Signals、Server Components，明天又冒出一个更快的打包器。好不容易把这些东西弄明白了，AI 又开始帮人写代码了。

有些前端朋友恐怕已经有点崩溃：**这还怎么学？到底有完没完？**

先别急着焦虑。

我写本书最初的技术展望时，还是 2020 年。那时候大家很兴奋，谈 Serverless，谈 Low-code，仿佛再过几年，服务器不用管了，程序员也不用敲代码了。

六年过去，结果如何？

服务器还在，程序员也还在。只不过服务器越来越多地交给云平台管理，写代码这件事，则多了一个叫 AI 的帮手。至于业务规则、权限、安全、性能、线上事故这些麻烦事，一件也没凭空消失。

**所以我觉得，2027 年前端最大的变化，不是又换了一个框架，而是“会写页面”和“能把产品做好”之间的差距，会越来越大。**

为什么这样说？下面我们慢慢聊。

## 01. 先看看，2026 年究竟发生了什么

先把能确定的事情摆出来，免得把技术预测写成算命。

截至 2026 年 11 月，比较值得前端朋友关注的进展有这些：

| 技术 | 已经发生的事 | 我觉得值得关注的地方 |
| --- | --- | --- |
| React | 发布了 React 19.3；React Compiler 1.0 已在此前推出 | 框架、编译器开始替你分担更多重复的优化工作 |
| Angular | 发布了 Angular v22，持续发展 Signals 等机制 | 数据变化后，究竟谁应该重新计算和更新页面 |
| TypeScript | 发布了采用原生实现的 TypeScript 7.0，7.1 Beta 也已推出 | 大项目的类型检查和开发工具终于有机会跑得更痛快 |
| Vite | Vite 8 使用 Rolldown 作为统一打包器 | 构建工具继续变快，但升级仍要考虑插件和兼容性 |
| Next.js | Next.js 16 系列发展了框架与部署平台之间的接口 | 服务端渲染、缓存、部署越来越难分开讨论 |
| 浏览器 | Container Queries、View Transitions 等能力越来越实用 | 一部分以前需要 JavaScript 库的事，浏览器自己就能干 |
| AI 编程 | GitHub 的编程代理进入修改仓库、运行检查、参与 PR 等流程 | AI 不只是补全代码，开始参与实际工程 |

这里我故意没有列一个“2026 年十大最火框架排行榜”。

为什么？因为排行榜每年都有，今天第一、明天第二，除了给各家粉丝提供吵架素材，对你手里的项目未必有多大帮助。

**技术的新旧，与项目的好坏，根本不是一回事。**

一个 Vue 老项目，运行稳定、用户满意、团队熟悉，你非要为了追新改成另一套框架，改了三个月，功能一点没增加，Bug 倒是多了十几个。这样的技术升级，我实在不知道该夸谁。

上面这些版本和进展来自官方公告，链接放在文末。下面才是我认为真正值得花时间弄明白的东西。

## 02. 前端的活，早就不只是“写个页面”

先举个简单的例子。

产品经理跑过来说：“帮我做个商品搜索页，要有输入框、商品列表、筛选和收藏。”

听起来不难，对吧？

写一个 input，调接口拿到 JSON，再把数据循环渲染出来。熟练一点的前端朋友，半天就能做出一个像模像样的 Demo。

但产品一上线，麻烦就来了。

用户输入“手”，又输入“手机”，紧接着输入“手机壳”。三个请求都发出去了。结果“手”的请求最慢，最后才回来。

**请问，页面应该显示“手”的结果，还是“手机壳”的结果？**

显然应该显示最新的搜索词。可如果你只是老老实实地把每个请求结果都写进页面，最后显示的可能偏偏是最早的那个。

再往下想：

用户没登录，点收藏怎么办？前端把按钮藏起来就算安全了吗？库存突然没了怎么提示？用户从详情页返回，筛选条件还在不在？点击筛选后页面一卡一卡的，是接口慢，还是 JavaScript 自己堵住了主线程？

问题一下子就多起来了。

比如处理搜索请求，可以用 `AbortController` 取消前一次不再需要的请求：

```js
let controller;

async function search(keyword) {
  // 新搜索开始，放弃上一轮尚未完成的请求
  controller?.abort();
  controller = new AbortController();

  try {
    const response = await fetch(
      '/api/search?q=' + encodeURIComponent(keyword),
      { signal: controller.signal }
    );

    if (!response.ok) {
      throw new Error('搜索接口出错了');
    }

    const goods = await response.json();
    renderGoods(goods);
  } catch (error) {
    if (error.name !== 'AbortError') {
      showError(error);
    }
  }
}
```

这只是演示核心思路。真实项目还应处理关键词防抖、空关键词、错误提示，以及请求取消和结果更新之间的竞态；必要时还要给结果加上请求序号，确保旧结果不能覆盖新结果。

你看，一个小小的搜索框，背后就牵扯到异步、网络、状态、用户体验。

**这才是未来前端工程师真正的基本功。**

AI 当然能帮你把输入框写出来。可这些业务细节，如果你自己都没想清楚，AI 凭什么知道你究竟想要什么？

## 03. React、Vue、Angular，别忙着站队

聊前端技术，似乎永远绕不开这三位。

React 的支持者觉得自己灵活，Vue 的支持者觉得自己省事，Angular 的支持者则觉得另外两家不够完整。争来争去，谁也不服谁。

我倒觉得，大家不妨先问一句：**你打算用它做什么？**

如果你们公司有十几个前端，已经把 Vue 3 用得很熟练，路由、状态管理、组件库都齐全，那么继续用 Vue 可能就是最省心的选择。

如果你做的是复杂交互产品，团队已经积累了大量 React 组件，还需要 React 生态里的全栈框架，那么 React 很合理。

如果团队规模很大，希望依赖注入、路由、表单、代码组织都遵守一套比较统一的约定，Angular 也有它的优势。

但我想提醒两件事。

### 1. React Compiler 不是万能的性能药

React Compiler 能帮助一些代码减少不必要的重复计算与渲染，这当然是好事。

但假设你的页面一次请求回来五万条数据，用户每点一下按钮，你就同步遍历五万条记录，最后再让浏览器画一大堆 DOM。

这时候，你把编译器请来，它也不可能凭空把五万条数据变成五十条。

编译器能优化一部分工作，**不能替你决定哪些工作根本不该做**。

### 2. Signals 不是换个名字就自动高性能

很多前端朋友一看到 Signals、响应式、细粒度更新，就觉得又要背一套新概念。

其实不妨把问题说得简单一点：

购物车里选中一件商品，总价变了。现在有十个组件，究竟哪几个需要重新计算？哪几个需要更新画面？谁负责记住“这个总价依赖于购物车”？

把这些问题搞懂，再去看 React、Vue、Angular 各自的实现，你会容易得多。

**我对 2027 年的判断：** 框架和编译器会继续帮开发者处理重复劳动。但最终谁更快，得拿真实项目测。只看演示视频里少写了多少代码，那是看热闹。

## 04. 网页到底让谁来画？浏览器还是服务器？

这个问题，今天比前几年更重要了。

前端朋友常见的 CSR、SSR、SSG、RSC，看着一堆英文缩写，确实有点烦。先把它们翻译成人话。

**CSR：** 主要由浏览器拿到 JavaScript 后生成页面。

**SSR：** 服务器先把页面 HTML 做出来，再发给浏览器。

**SSG：** 提前在构建时生成 HTML，需要时直接拿现成的页面。

**RSC（React Server Components）：** 在支持它的 React 框架中，一部分组件放在服务器执行，结果再交给客户端使用。注意，RSC 和 SSR 不是同一个概念，不能混着说。

哪种最好？

我认为这个问题本身就问得不太好。

假设你做一家电商网站。商品介绍页希望搜索引擎能收录，可以考虑由服务器先生成内容；购物车里的勾选、数量变化，需要浏览器快速响应；公司内部那个只有员工才能访问的后台，可能根本用不着复杂的服务端组件。

**该在服务器做的，让服务器做；该在浏览器做的，让浏览器做。**

这话听着像废话，却真有不少项目做不到。

尤其要小心缓存。

服务器生成的商品介绍可以被很多人共享，但用户的收货地址、订单信息可千万不能搞混。假如因为缓存配置错误，让用户 A 看到了用户 B 的订单，页面加载速度再快，那也是一场事故。

所以我更看重一名工程师能否说清楚：**数据在哪获取、结果缓存多久、什么时候失效、哪些数据绝不能跨用户共享。**

至于项目用了 SSR 还是 CSR，反倒是后面才需要回答的问题。

## 05. 浏览器自己能做的事，别急着装库

我发现，前端工程师有时候有个挺有意思的习惯：遇到问题，第一反应是先找一个 npm 包。

页面过渡动画，找个库；响应式布局，找个库；弹窗，找个库；甚至有些原生 API 几行就能解决的事，也要先装个库。

结果项目 `package.json` 越来越长，依赖之间打架，升级一次像拆炸弹。

现在浏览器自己的本事越来越大了。

例如 Container Queries。以前我们根据屏幕宽度决定卡片如何排版，但同一张卡片可能被放进很宽的内容区，也可能被放进很窄的侧边栏。屏幕宽度没变，卡片能用的空间却完全不同。

这时可以直接根据**容器自己的宽度**来调整布局：

```css
.product-card {
  container-type: inline-size;
}

.product-layout {
  display: block;
}

@container (min-width: 36rem) {
  .product-layout {
    display: grid;
    grid-template-columns: 12rem 1fr;
    gap: 1rem;
  }
}
```

这段 CSS 不复杂，关键在于思路：不用在 JavaScript 里天天监听窗口宽度，布局本来就是 CSS 擅长的事，那就交给它。

当然，不能走向另一个极端。自己 Chrome 支持，不代表所有用户手机上的浏览器都支持。

用新特性前，查一下 [Baseline](https://web.dev/baseline) 和项目目标浏览器范围；不支持时，安排好降级。

**我觉得未来一两年，懂浏览器原生能力的人，反而有机会写出依赖更少、维护更轻松的前端代码。**

## 06. TypeScript 7、Vite 8：开发工具变快，值得高兴，但别高兴太早

2026 年，TypeScript 和 Vite 都有重要进展。

TypeScript 7 换上原生实现，Vite 8 使用 Rolldown。一个致力于改善类型检查和编辑器体验，一个继续优化构建链。

这些变化我当然欢迎。

想想看，改两行代码，编辑器转圈半天；启动项目，先去倒杯水；打个包，够你吃一顿饭。这样的开发体验，实在很难让人热爱 coding。

不过，工具跑得快，不等于你的页面就自动跑得快。

你们团队准备升级 Vite，我建议先别急着开庆功会，拿数据说话：

- 开发服务器第一次启动，究竟快了多少？
- 改一个组件后，页面热更新要多久？
- 正式环境打包耗时多少，产物有没有变大？
- 插件、动态导入、环境变量、CI 是否都正常？

**如果构建快了 30%，却因此引入线上 Bug，这次升级恐怕就不是赚了。**

至于 TypeScript，我更希望大家把注意力放在**类型设计**上，而不是只记新版本号。

比如订单状态：

```ts
type OrderStatus = 'pending' | 'paid' | 'cancelled';

type Order = {
  id: string;
  status: OrderStatus;
};

function canRefund(order: Order): boolean {
  return order.status === 'paid';
}
```

这段代码的好处很直接：订单的状态只能是约定好的几种值，很多拼写错误和漏处理的分支能在开发阶段更早暴露。

但还得提醒一句：**TypeScript 不是运行时保安。** 如果后端真的返回了 `status: 'unknown'`，类型声明不会自动拦截它。外部数据仍然需要校验。

我对 2027 年的判断是：会写 TypeScript 逐渐变成基本要求，**能不能把类型、数据校验和工具链一起设计好**，才更能体现水平。

## 07. 性能优化，别只盯着打包体积

前端性能这件事，真是个老问题了。

有朋友可能会说：“我已经做了代码分割，打包体积也缩小了，怎么用户还是说卡？”

因为页面卡不卡，和 JS 包大小有关，但远远不止这一件事。

举个例子。

用户点击“加入购物车”。接口很快，100 毫秒就返回了。结果页面还是两秒钟才动一下。

为什么？

可能事件函数里进行了大量同步计算，也可能一次状态更新牵连了太多组件，还可能是布局计算和绘制花了很长时间。

所以性能排查，应该顺着用户的一次操作往下看：

**用户点击 → 主线程有没有空 → 事件代码执行多久 → 状态更新耗时多少 → 页面什么时候真正画出来。**

你得找到慢在哪一步，而不是心血来潮给所有组件套上 `useMemo`。

现在经常提到的 Core Web Vitals，至少要认识三个指标：

- **LCP：** 页面的主要内容多久显示出来。
- **INP：** 用户操作后，到页面给出可见反馈用了多久。
- **CLS：** 页面有没有莫名其妙地跳来跳去。

这些东西不能光在自己的电脑上测。你坐在高性能电脑前，网络也快，用户可能拿着几年以前的手机坐地铁。两个人看到的根本不是同一个世界。

下面用 `web-vitals` 库演示一个最简采集入口。`/api/vitals` 需要由你自己的后端实现：

```js
import { onCLS, onINP, onLCP } from 'web-vitals';

function report(metric) {
  navigator.sendBeacon(
    '/api/vitals',
    JSON.stringify({
      name: metric.name,
      value: metric.value,
      id: metric.id
    })
  );
}

onLCP(report);
onINP(report);
onCLS(report);
```

这不是完整的监控系统。真正上线还得考虑数据采样、页面离开时的上报、隐私脱敏、异常过滤和后端统计。

**我觉得，能拿出一份真实用户的性能数据，找到一次卡顿的根源，最后证明自己确实修好了，比简历上写十条“精通性能优化”都有说服力。**

## 08. AI 来了，前端工程师究竟该怎么办？

我猜这是很多朋友最关心的问题。

以前写代码，常常为了一个细节翻文档、搜 Stack Overflow。现在你把需求描述给 AI，一会儿就能吐出几百行代码，连单元测试都能顺手给你生成一些。

效率提升了吗？很多场景下，确实提升了。

那么是不是说，前端工程师很快就没饭吃了？

我不敢这么武断。因为我越来越觉得，**会生成代码和能交付一个靠谱的产品，相差还挺远。**

假设你让 AI 做一件小事：给订单详情页加一个“取消订单”按钮。

如果你只说“加一个按钮，点了取消订单”，AI 可能很快就做完了。

但下面这些问题，谁来考虑？

订单已经支付了，还能取消吗？已经发货了怎么办？用户连点两次，会不会重复发请求？网络超时以后，订单究竟取消成功没有？前端隐藏按钮，后端是不是也应该校验权限？

如果这些都没说清楚，AI 写得再快，可能也只是更快地制造 Bug。

所以我建议大家学会给 AI 交代清楚任务，别把它当许愿池：

```text
需求：订单详情页增加“取消订单”功能。

业务规则：
1. 只允许取消 pending 状态的订单。
2. 后端必须重新校验订单归属和状态。
3. 连续点击不能重复提交。
4. 接口失败要恢复按钮，并提示用户。
5. 不改动支付和退款逻辑。

完成标准：
- 覆盖 pending、paid、cancelled 三种状态。
- 测试重复点击与网络失败。
- 检查手机窄屏与键盘操作。
- 给出测试结果，说明如何回滚。
```

你看，同样是一个按钮，需求写清楚和没写清楚，结果可能天差地别。

而且还有一件事很重要：AI 代理会读网页、看仓库、调用工具，这些东西并不一定可信。不要把外部文档里的指令当成系统命令，更别随便把部署密钥、客户数据和支付权限一股脑交给它。

**我的判断：** 2027 年，写代码的重复劳动会进一步减少，但需求拆解、代码审查、测试、排错和安全责任会变得更重要。

别光看 AI 一次写了多少行代码。**最终要看项目是否真的少返工、少出事故、上线更快。**

## 09. 安全、无障碍、隐私，听着不酷，但真出事就不酷了

有些技术，发布会上讲出来很有气势；有些技术，平时大家不爱聊，出事时却能把整个团队折腾得够呛。

比如安全。

前端把商品价格显示成 100 元，用户打开开发者工具，改成 1 元再提交。后端要是直接相信前端传过去的数字，那可就热闹了。

所以我一直认为，**前端可以负责交互，但真正涉及权限、金额、订单状态等重要规则，后端一定要独立校验。**

再比如无障碍。

一个弹窗做得漂亮极了，动画丝滑、阴影精致，结果用户用键盘进得去、出不来。做页面的人觉得这是小事，真正需要键盘操作的人可就麻烦了。

还有用户隐私。

现在很多团队把日志、性能数据、异常截图、AI 提示词一股脑收集。方便是方便，但客户的个人信息、令牌、支付相关内容也可能跟着被传出去。

这些问题，不会因为你用了最新的框架就自动解决。

我建议至少把几件事当成日常习惯：**服务端做权限校验、关键流程有测试、弹窗能用键盘操作、部署可以回滚、日志不乱收敏感数据。**

你可能觉得这几句话一点也不“前沿”。

可如果一个项目连这些都做不好，讨论下一代框架，多少有点本末倒置。

## 10. WebGPU、浏览器端 AI，这些东西值不值得学？

值得关注，但不必人人都冲进去。

WebGPU 已在主要浏览器中得到支持，能够用 GPU 做图形和部分通用计算。一些浏览器端 AI 推理工具也开始利用它。

看到这里，很多朋友又开始紧张了：是不是明年找前端工作，不会 WebGPU 就没机会了？

我觉得大可不必。

如果你主要做企业管理系统，每天和表单、权限、订单、表格打交道，那么把数据模型、性能、测试做好，可能比急着研究 GPU 着色器更划算。

但如果你做在线设计工具、3D 编辑器、地图、视频处理，甚至希望某些 AI 功能在用户设备上直接运行，那 WebGPU 和 WebAssembly 就有必要认真研究。

还得提醒一句：**浏览器支持 WebGPU，不等于所有电脑都能流畅运行大模型。**

硬件能力、显存和内存、驱动、耗电、模型下载时间，这些都要算进去。

所以面对新技术，我习惯问一句：**这东西究竟解决我手里的什么问题？**

回答不上来，先放进“了解一下”的清单就好，没必要立刻把整个技术栈推倒重来。

## 11. 说说我对 2027 年的三个判断

前面谈的主要是已经发生的事。下面三个判断，只代表我的推测。等过一年回头看，错了就是错了，没必要硬解释。

**第一，前端框架不会消失，但只会一个框架越来越不够用。**

这里不是说你要把 React、Vue、Angular 全学一遍。

恰恰相反，我更赞成先把一套主力框架学深，然后弄明白浏览器、网络、数据、渲染、缓存、构建、部署如何协同工作。

要检验这个判断，可以看未来一年主流框架的官方路线图和企业招聘要求，是不是越来越强调完整系统的工程能力。

**第二，AI 会越来越擅长做重复的开发工作，但无法替你承担业务责任。**

代码可以生成，需求也可以让 AI 帮忙分析。但用户被扣错了钱、隐私被泄露、项目上线就崩，总不能说“这段是 AI 写的，所以和我无关”。

判断 AI 到底有没有帮上忙，应该看一个团队从需求到上线用了多少时间、返工了几次、线上出了多少问题。

**第三，浏览器原生能力会继续吃掉一部分小工具的工作。**

布局、动画、原生组件和设备能力越来越丰富，一部分以前非装库不可的需求，可能只要几行 CSS 或一个浏览器 API 就能完成。

验证方法很简单：拿真实需求试试原生方案，再比较兼容性、效果、包体积和维护成本。

我不会在这里喊“React 要完蛋了”“前端马上消失了”这种口号。听着刺激，拿来做职业规划却不太靠谱。

## 12. 如果让我现在重新学前端，我会怎么安排？

有朋友可能会问：“道理都明白，可我现在学什么？总不能什么都学吧？”

当然不能。人的时间又不是无限的。

如果你是刚入行的朋友，我建议先用三个月把一套东西真正跑通。

**第一个月，老老实实补 JavaScript 和浏览器基础。**

函数、闭包、异步、事件循环、TypeScript、HTTP、DOM，这些东西也许不够时髦，却能解释很多莫名其妙的 Bug。

别只刷题。做个搜索页面，带筛选、分页、错误处理，亲手遇到几次请求竞态，比看十篇“异步编程终极指南”管用。

**第二个月，选一个框架，把一个小项目做完整。**

React 或 Vue 都可以。做商品列表、详情页、购物车。弄明白状态放哪、接口怎么拿数据、页面怎么渲染、缓存什么时候失效。

暂时别为了炫耀技术，把一个简单项目搞成十几个仓库。

**第三个月，给这个项目补上真正的工程能力。**

测一次真实性能；补几条关键路径测试；检查键盘操作和错误提示；用 AI 代理完成一次有明确验收标准的修改；最后部署上线，确保出错时可以回滚。

如果你已经有五年、十年的工作经验，那就别跟着这份计划从 `for` 循环重新学一遍了。

你应该找自己最薄弱的地方。

线上总是卡，就钻研浏览器性能；升级一次工具链就鸡飞狗跳，就补构建和 CI；订单数据经常乱，就去弄懂异步、缓存和一致性；团队开始使用 AI，就把任务拆解、代码评审和测试体系建起来。

**会十种框架，却说不清自己修过什么实际问题，我觉得没什么好骄傲的。**

相反，一个人只熟悉一套框架，却能把一次线上故障从原因到修复、验证、预防讲得清清楚楚，我会觉得他技术相当扎实。

## 写在最后

写这本《前端内参》，我一直有一个很简单的想法：与其整天追着新名词跑，不如把最基础、最重要的东西真正学透。

前端发展到今天，变化确实比过去快多了。框架不断升级，编译器越来越快，AI 已经能替人写不少代码。

这些变化，我是欢迎的。

毕竟，程序员不该把人生都消耗在重复敲代码、修改配置、等待构建上面。如果工具能替我们做掉这些事，我们就能把更多时间用在真正有意思、也更有挑战的问题上。

但我不希望大家因此产生一个误会：以为工具越来越聪明，自己就可以不用动脑子。

恰恰相反。

**工具越厉害，你越要知道自己想做什么、为什么这样做、怎样才算做好。**

否则今天被一个框架牵着鼻子走，明天又被一个 AI 工具牵着鼻子走。折腾了一大圈，技术栈倒是换了好几轮，解决实际问题的能力却没增长多少。

我始终觉得，coding 是一件可以干到老、而且越干越有意思的事情。

前提是，我们不能只满足于会用工具，还要努力成为真正理解技术的人。

**2027 年，我最看好的不是哪一个框架，而是那些还愿意认真思考、认真写代码、认真解决问题的程序员。**
