# 捌.1 TypeScript：类型系统能替你挡住多少 Bug？

你写了十年 JavaScript，当然知道它灵活。灵活到什么程度？接口说会返回数字，后端今天却送来一个字符串；程序照样能启动，直到用户点按钮才炸。

TypeScript 的好处，是尽量让这类问题**在写代码的时候就暴露出来**。不过，它也有一条很清楚的边界：**类型检查不能替你验证真实网络数据。**

## 01. 一个常见误会

```typescript
type User = {
  id: number;
  name: string;
};

const raw: unknown = JSON.parse('{"id":"123","name":"小王"}');
// raw 目前是 unknown；不能直接认定它符合 User
```

你可能想写 `const user = raw as User`，一下就通过了类型检查。可 `as` 是类型断言，**不是运行时的数据转换**。字符串 `"123"` 不会神奇地变成数字 `123`。

那怎么办？需要真正检查数据：

```typescript
type User = { id: number; name: string };

function isUser(value: unknown): value is User {
  if (typeof value !== "object" || value === null) return false;
  const item = value as Record<string, unknown>;
  return Number.isInteger(item.id) && typeof item.name === "string";
}

function parseUser(value: unknown): User {
  if (!isUser(value)) throw new TypeError("接口返回的用户数据不合法");
  return value;
}

const raw: unknown = JSON.parse('{"id":123,"name":"小王"}');
console.log(parseUser(raw).name); // >> 小王
```

这一段代码，`unknown` 的意思就是：我还不知道它究竟是什么，先别乱用。

`isUser()` 负责运行时检查，检查通过后，TypeScript 才允许按 `User` 类型继续使用它。

**这套检查仅覆盖示例里的两个字段。** 真正的业务还要根据需求检查字符串长度、数字范围、枚举值等；数据复杂时也可以使用成熟的校验库。

## 02. any 和 unknown 到底差在哪？

`any` 基本上是告诉编译器：“你别管，我自己负责。”问题是你明明没管好，编译器也很难提醒你。

`unknown` 则要求你在使用之前先证明这个值符合预期。

我建议外部接口、第三方 SDK、不受信任的本地存储数据，都从 `unknown` 开始处理，别直接拿 `as` 蒙混过关。

## 03. 练习：AI 写的代码安全吗？

让 AI 生成一个 `getUser(): Promise<User>`，然后故意让接口返回：

```json
{"id":null,"name":12}
```

如果 AI 只是把 `await response.json()` 强转成 `User`，那它并没有解决真实数据安全问题。

你的任务是：让它在数据不合法时给出明确错误，并写出至少两条测试用例。
